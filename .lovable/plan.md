## Root cause (verified)

`src/lib/store.ts` line 702 hard-blocks the client store from ever bootstrapping when the URL starts with `/passenger/`:

```ts
if (window.location.pathname.startsWith("/passenger/")) return;
```

Flow for "View Passenger Portal":

1. `src/routes/delivery.$deliveryId.tsx` calls `ensurePassengerToken(deliveryId)`, which lazily creates a `WorkflowRecord` with a unique token in the store, then pushes to Supabase via `scheduleRemotePush`.
2. It opens `/passenger/{token}` in a new tab.
3. The new tab loads `src/routes/passenger.$token.tsx`. Its loader calls `getPassengerViewByToken` — in the sandbox this returns `{ found: false, … }` because the service-role key is missing (already confirmed in the previous fix).
4. `TokenPortal` then falls back to `useStore(s => s.workflow.find(w => w.token === token))`.
5. But `ensureBootstrap` short-circuits on `/passenger/`, so the store never hydrates from Supabase. `state.workflow` is empty (or only seed defaults). No record has the freshly generated token → `TokenNotFound` renders.

This affects every case (Hassan, Laila, all) equally — it is a store-hydration bug, not a per-case token bug. Tokens are generated correctly and stored on the workflow record; the passenger route just can't see them.

Also verified:
- Tokens are per-delivery, generated by `generateTrackingToken(deliveryId)` in `ensureWorkflow`. No hardcoded demo tokens.
- `View Passenger Portal` in `src/routes/delivery.$deliveryId.tsx` already opens the correct `/passenger/${token}` URL for the selected case.
- `persistence.ts::initPersistence` already gates the actual Supabase read on `session !== null`; unauthenticated passengers can't pull the staff snapshot even if `ensureBootstrap` runs (RLS + client guard).

## Fix (single file, no DB, no UI)

**`src/lib/store.ts` — `ensureBootstrap()`**

Remove the `/passenger/` early-return. Rationale:

- Staff previewing a token from Delivery Management are already authenticated. Removing the guard lets `initPersistence` hydrate their store from Supabase, so the client-side fallback in `TokenPortal` finds the workflow record for the token and renders the correct case.
- Real passengers hitting the SMS/WhatsApp link are unauthenticated. `initPersistence` sees no session, skips the `bootstrap()` read, and never pushes state. The store stays at the local `defaults()` (which contains no live case data now that demo tokens were removed). Their token-scoped view still comes from `getPassengerViewByToken` (service role) in production.
- The privacy concern in the removed comment is already enforced structurally by RLS + the session check inside `initPersistence`; the pathname guard is redundant and is what breaks staff preview.

After the change:
- Hassan's card in Delivery → opens `/passenger/{hassan-token}` → store hydrates → fallback resolves Hassan's workflow → Passenger Portal renders Hassan.
- Same for Laila and every other case, using the token stored on that case's workflow record.

## Verification

- Playwright: sign in as staff, open a delivery detail, click "View Passenger Portal" for two distinct cases, assert each new tab renders the correct passenger name (no `TokenNotFound`).
- Playwright: visit `/passenger/not-a-valid-token` → still renders `TokenNotFound` (guard preserved by the route component, not by bootstrap).
- `bunx tsgo --noEmit` passes.

No UI, schema, SQL, or design changes.
